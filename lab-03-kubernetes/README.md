# Лабораторная работа №3: Платформа shop в Kubernetes (политики, Helm, оператор БД, отказоустойчивость, мониторинг)

- **Язык сервисов:** Go 1.27
- **Стенд:** Kubernetes-кластер OrbStack
- **Инструменты развертывания:** Helm v4
- **Движок политик:** Kyverno
- **Namespace приложения:** shop
- **Namespace мониторинга:** monitoring (стек из Лабораторной работы №2)

---

## Введение и цель работы

В реальном кластере разработчики могут задеплоить сервис без лимитов ресурсов, с образом из недоверенного реестра или без обязательных меток — и это дойдёт до прода, потому что ревьюить каждый YAML вручную нереально. Развёртывание и восстановление базы данных требует ручной работы инженера. А при падении control plane никто заранее не знает, что из приложения упадёт вместе с ним, а что продолжит отвечать — это выясняется уже во время инцидента.

Работа закрывает три проблемы:

1. **Ограждения на уровне кластера.** Движок политик Kyverno физически не даёт применить манифест, нарушающий правила. Ручное ревью YAML больше не нужно.
2. **Эксплуатация БД через оператора.** PostgreSQL разворачивается не вручную, а оператором (CloudNativePG или Zalando postgres-operator), который сам восстанавливает поды, делает бэкапы и следит за состоянием.
3. **Проверка поведения при падении control plane.** На живом кластере проверяется, что приложение продолжает отвечать, пока control plane лежит, и снова становится управляемым после восстановления.

Дополнительно в чарт shop встраиваются объекты мониторинга `ServiceMonitor` и `PrometheusRule`, работающие поверх стека из Лабораторной работы №2 (новый стек не поднимается).

**Стенд:** локальный кластер Kubernetes (kind / k3d / minikube / OrbStack), без облака.

### Выбор движка политик: Kyverno

Рассматривались два варианта — Kyverno и OPA/Gatekeeper.

**Kyverno** пишет правила обычными Kubernetes-манифестами в YAML. Синтаксис тот же, что и у чарта shop, поэтому не нужно учить отдельный язык. Устанавливается одной командой в локальный кластер, потребляет мало ресурсов. Отчёты о нарушениях (`PolicyReport`) доступны через `kubectl get policyreport` — удобно для скриншотов. Встроенные `ClusterPolicy` с типом `validate` покрывают все пять требуемых правил без дополнительных утилит.

**OPA/Gatekeeper** пишет правила на Rego — отдельном DSL. Мощнее и гибче для сложной логики, но требует времени на освоение. В локальном кластере потребляет больше ресурсов: нужен отдельный admission-контроллер.

**Выбор: Kyverno.** Основные причины — низкий порог входа (правила как манифесты), лёгкость для локального кластера OrbStack, встроенные отчёты о нарушениях из коробки.

## Часть 0 — Сервисы api и worker

Для реализации микросервисной архитектуры приложения `shop` проект был разделен на два независимых компонента со следующими зонами ответственности:

1. **`api`** — синхронный слой, принимающий входящий HTTP-трафик, валидирующий запросы и фиксирующий заказы в базе данных.
2. **`worker`** — асинхронный слой, выполняющий фоновую обработку накопившихся в очереди заказов.

Общая бизнес-логика (работа с СУБД) и сквозной функционал наблюдаемости (observability) вынесены в изолированный внутренний пакет `internal/`, что исключает дублирование кода и обеспечивает консистентность метрик.

### Шаг 0.1. Инициализация и настройка окружения Go

Разработка ведется в изолированной ветке `lab-03`. Инициализация проекта выполнена в корневом каталоге лабораторной работы командой:

```bash
go mod init shop
```

Созданный файл `go.mod` определяет имя базового модуля как `shop`. Это позволяет использовать детерминированные абсолютные пути для внутренних импортов (например, `import "shop/internal/telemetry"`) во всех подпапках проекта.

### Шаг 0.2. Разработка исходного кода компонентов

#### 1. Сервис API (`cmd/api/main.go`)

Реализован как HTTP-сервер, слушающий порт `8080`. Внедрены следующие эндпоинты:

- `GET /health` — readiness- и liveness-проба. Содержит триггер искусственного отказа: при наличии переменной окружения `HEALTH_FAIL=true` возвращает статус `503 Service Unavailable` вместо стандартного `200 OK`. Данная логика необходима для эмуляции зависания процесса обновления (`rolling update`) в последующих частях работы.
- `POST /order` — принимает JSON-манифест вида `{"description": "..."}`. Генерирует транзакцию на запись в PostgreSQL и возвращает идентификатор созданной записи `{"id": N}` со статусом `201 Created`.
- `GET /orders` — возвращает JSON-массив всех существующих заказов, отсортированных по времени создания по убыванию (свежие сверху).
- `GET /metrics` — эндпоинт экспорта метрик для Prometheus.

---

#### 2. Фоновый воркер (`cmd/worker/main.go`)

Реализован как демон (background worker). Процесс запускает бесконечный цикл с интервалом в 2 секунды, запрашивает из PostgreSQL один необработанный заказ и переводит его в статус обработанного.

Для обеспечения бесшовной интеграции с инфраструктурой Kubernetes, воркер параллельно поднимает собственный HTTP-сервер на порту `8081`, обслуживающий ручки `GET /health` (для контроля жизнедеятельности пода планировщиком кластера) и `GET /metrics`.

---

#### 3. Общие модули (`internal/`)

- `db/db.go` — реализует пул соединений через драйвер `pgxpool`. Инжектирован отказоустойчивый механизм подключения: при старте сервис выполняет до 30 попыток соединения с интервалом в 2 секунды, что гарантирует успешный запуск при долгой инициализации пода СУБД. На уровне SQL-запросов конкурентная обработка реализована через конструкцию `SELECT ... FOR UPDATE SKIP LOCKED` — это позволяет безопасно масштабировать количество реплик воркера без риска возникновения race condition и double-processing.
- `telemetry/telemetry.go` — подсистема мониторинга. Логирование переведено на структурированный формат JSON через стандартный пакет `slog`. Имена RED-метрик (`http_requests_total`, `http_request_duration_seconds`) полностью сохранены из Лабораторной работы №2, что обеспечивает автоматическую интеграцию с уже существующим дашбордом Grafana без необходимости его пересборки. Экспорт распределенных трассировок в Jaeger по протоколу OTLP выполнен с обработкой исключений: при отсутствии переменной `OTEL_EXPORTER_OTLP_ENDPOINT` подсистема трейсинга мягко отключается, не блокируя запуск основного рантайма.

### Шаг 0.5. Многоэтапная сборка Docker-образов

Для минимизации поверхности атаки и оптимизации размера артефактов настроен Multi-stage `Dockerfile`. Компиляция статических бинарников выполняется в едином builder-контейнере (`golang:1.27-alpine`) с отключением CGO и оптимизацией таблиц символов: `CGO_ENABLED=0 GOOS=linux go build -ldflags "-s -w"`.

Дистрибуция компонентов изолирована на этапе сборки через пустые базовые образы `FROM scratch`. Итоговые контейнеры собираются независимо с применением целевого флага `--target`:

```bash
docker build --target api    -t shop-api:1.0.0    .
docker build --target worker -t shop-worker:1.0.0 .
```

Помимо исполняемых файлов, в каждый `scratch`-контейнер из этапа сборщика принудительно инжектируется файл системных корневых сертификатов `/etc/ssl/certs/ca-certificates.crt`. Это необходимо для корректной верификации TLS-сессий Go-драйвером базы данных при защищенном подключении к пулу PostgreSQL внутри кластера. При запуске конвейера сборки без указания параметра `--target` Docker автоматически скомпилирует только финальный стейдж (`worker`).

### Шаг 1.5. Правило: запрет privileged-контейнеров

Создана политика `no-privileged`, запрещающая вызов параметров `securityContext.privileged: true` и `allowPrivilegeEscalation: true`. Привилегированный контейнер стирает грань между изолированной песочницей пода и операционной системой ноды, получая доступ к процессам хоста, сетевым интерфейсам и возможности монтирования дисков. Поле `allowPrivilegeEscalation` управляет возможностью скрытого повышения прав процесса внутри контейнера через `setuid`-бинарники; правило требует его значения `false`.

Файл: `policies/04_no_privileged.yaml`.

```bash
kubectl apply -f policies/04_no_privileged.yaml
```

Валидация контура безопасности выполнена с помощью манифеста `policies/violations/04_privileged.yaml`, запрашивающего повышенные привилегии. Запрос успешно отклонён admission-webhook'ом:

```bash
kubectl apply -f policies/violations/04_privileged.yaml
```

![](img/06_violation_privileged.png)

При интеграционном тестировании шага 1.6 обнаружена ловушка conditional anchor: при отсутствии блока `securityContext` в контейнере правило падало на пути `/spec/containers/0/securityContext/`, потому что Kyverno ожидал наличия родительского ключа.

Поля `privileged` и `allowPrivilegeEscalation` опциональны — если их нет, под пропускается (дефолт `false`). Отклоняются только явно выставленные `true` за счёт каскадного условного оператора `=(securityContext)` на уровне родителя: если блока нет — правило пропускает контейнер, если есть — проверяет вложенные `=(privileged): false` и `=(allowPrivilegeEscalation): false`.

### Шаг 1.6. Правило: запрет latest-тега

Создана политика `no-latest-tag`, запрещающая образы с тегом `:latest` и образы без тега. Тег `latest` не даёт понять, какая версия реально запущена, и делает невозможным `helm rollback` - откатываться некуда.

Файл: `policies/05_no_latest_tag.yaml`.

Политика содержит два правила:

- `require-image-tag` - pattern `image: "*:*"` - требует наличия тега;
- `validate-no-latest` - pattern `image: "!*:latest"` - запрещает явный `:latest`.

```bash
kubectl apply -f policies/05_no_latest_tag.yaml
```

Проверка манифестом `policies/violations/05_latest_tag.yaml` с образом `nginx:latest`. Запрос успешно отклонён правилом `validate-no-latest` без ложных срабатываний со стороны политики `no-privileged`:

```bash
kubectl apply -f policies/violations/05_latest_tag.yaml
```

![](img/07_violation_latest_tag.png)

## Часть 2 — Чарт api и worker

### Шаг 2.1. Каркас Helm-чарта

Перед сборкой чарта удалены устаревшие ресурсы Лабораторной работы №2 из namespace `monitoring` - старый `api-deployment`, `api-service` и `api-servicemonitor`. Они конфликтовали бы с новым API по меткам `app=api-server` и имени Service.

```bash
kubectl delete deployment api-deployment -n monitoring
kubectl delete service api-service -n monitoring
kubectl delete servicemonitor api-servicemonitor -n monitoring
```

Собран Helm-чарт платформы `shop` с метаданными `Chart.yaml`, параметрами `values.yaml` и четырьмя шаблонами в `templates/`: `Deployment` и `Service` для `api` и `worker`. Изменяемые параметры - реплики (api 3, worker 2 по умолчанию), образы, лимиты ресурсов, порты, метка владельца, реквизиты Postgres и адрес OTel-коллектора - вынесены в `values.yaml`.

В шаблоны сразу заложены требования правил безопасности Части 1: обязательные метки `app` и `owner`, ресурсные `requests` и `limits`, доверенные образы `shop-api:1.0.0` и `shop-worker:1.0.0` с явным тегом и `imagePullPolicy: Never`. Оба `Deployment` используют стратегию `RollingUpdate` с `maxSurge: 1` и `maxUnavailable: 0` - обновление строго по одному поду без простоя. Пробы `readiness` и `liveness` настроены на `/health` (api - порт 8080, worker - 8081).

Чарт проверен статически:

```bash
helm lint charts/shop
helm template shop charts/shop -n shop
```

Утилита `helm lint` завершается без ошибок, а `helm template` корректно рендерит все четыре объекта с подставленными значениями из `values.yaml`.

### Шаг 2.2. Установка чарта и прохождение контроля политик

Установка Helm-чарта выполнена в изолированный namespace `shop` с автоматическим созданием целевого пространства имен:

```bash
helm install shop charts/shop -n shop --create-namespace
```

Все пять разработанных политик Kyverno в режиме `Enforce` успешно пропустили манифесты приложений — первичная установка завершилась без отклонений со стороны admission-webhook.

Однако на этапе рантайма поды `api` и `worker` ушли в циклическую перезагрузку `CrashLoopBackOff`. Причина: кодовая база сервисов требует обязательного подключения к СУБД Postgres при инициализации пула, в то время как по исходной методичке база данных разворачивается только в Части 3.

Для устранения архитектурного тупика и успешного прохождения тестов Части 2 (работающие readiness-пробы на ручке `/health`), в шаблоны чарта внедрен временный одиночный Postgres (`templates/postgres-temporary.yaml`), состоящий из `Deployment shop-postgres` и `Service shop-postgres-rw`. Параметры его конфигурации и учетные записи (`app`, `app-password`) полностью синхронизированы через `values.yaml`.

После применения обновлений выполнен точечный сброс экспоненциальных таймаутов `CrashLoopBackOff` для приложений:

```bash
helm upgrade shop charts/shop -n shop
kubectl rollout restart deployment api -n shop
kubectl rollout restart deployment worker -n shop
```

Валидация финального состояния компонентов платформы:

```bash
kubectl get pods -n shop
```

![](img/09_shop_pods_running.png)

Все шесть подов платформы (3 реплики `api`, 2 реплики `worker` и 1 под временной СУБД) успешно перешли в стабильный статус `1/1 Running` с нулевым счетчиком рестартов.

### Шаг 2.4. Rolling update без простоя

Проверена стратегия бесшовного обновления `api` под нагрузкой. Тег образа в файле `charts/shop/values.yaml` изменен с `1.0.0` на `1.0.1`:

![](img/15_rolling_update_values_1_0_1.png)

Для контроля доступности сервиса внутри кластера запущен под `curl-test`, непрерывно опрашивающий эндпоинт `/health` через внутренний Service:

Применено обновление релиза:

```bash

```

Благодаря стратегии `RollingUpdate` с параметрами `maxSurge: 1` и `maxUnavailable: 0`, контроллер Deployment запускал новые поды строго по одному и не выводил из эксплуатации старые до успешного прохождения `readinessProbe`.

Зафиксировано переходное состояние — одновременная работа новых (`api-7f494fb94f-*`) и старых (`api-8585f9978d-*`) подов:

### Шаг 2.5. Сломанный релиз и антикризисный откат (Rollback)

Проведена эмуляция некорректного обновления. В конфигурационном файле `charts/shop/values.yaml` для сервиса `api` параметр `healthFail` переведен в значение `"true"` (в контейнере переменная `HEALTH_FAIL=true`), что переключает эндпоинт `/health` на возврат кода `503 Service Unavailable`:

![](img/18_rollback_values_healthfail.png)

Применено обновление релиза:

```bash
helm upgrade shop charts/shop -n shop
```

Контроллер Deployment создал один новый под (`api-56c88c4fd4-l6bn7`), который не прошел `readinessProbe`. Из-за параметров стратегии `maxUnavailable: 0` процесс обновления остановился: старые исправные поды не выводились из эксплуатации, а новый под не был подключен к эндпоинтам Service и не получал трафик.

Фиксация заблокированного статуса деплоя:

```bash
kubectl get pods -n shop -l app=api-server
kubectl rollout status deployment api -n shop
```

![](img/19_rollout_stuck.png)

Во время блокировки обновления сервис продолжал бесперебойно обслуживать запросы. Временный под `curl-test` на протяжении всего инцидента фиксировал ответы `200` на `/health` через внутренний Service:

![](img/20_health_200_during_failure.png)

Выполнен ручной откат релиза Helm на предыдущую стабильную ревизию:

```bash
helm rollback shop -n shop
```

Валидация состояния кластера после восстановления:

```bash
kubectl get pods -n shop -l app=api-server
kubectl rollout status deployment api -n shop
```

![](img/21_rollback_success.png)

Сломанный под удален, три пода из предыдущей рабочей ревизии вернулись в штатный режим работы, команда `rollout status` завершилась успешно. Простой сервиса составил 0 секунд. Часть 2 полностью закрыта.

### Шаг 3.3. Проверка reconciliation оператора

## Часть 4 — Падение control plane

### Шаг 4.1. Остановка etcd (или apiserver)

Останавливаем ключевой компонент control plane. Проверяем, что кластер теряет управляемость — `kubectl apply` и `helm upgrade` не проходят.

### Шаг 4.2. Проверка, что приложение живо

Пока control plane лежит, дёргаем `/health` и `/orders` у api, `/health` у worker, коннектимся к postgres. Приложение продолжает отвечать — kubelet на нодах работает независимо от мозга.

---

### Шаг 4.3. Восстановление control plane

Возвращаем etcd/apiserver. Убеждаемся, что кластер снова управляем: `kubectl get nodes` отвечает, `helm upgrade` проходит.
