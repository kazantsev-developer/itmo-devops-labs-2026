## Введение и цель работы. Сюжетная арка: Конвейер

Заглянем за кулисы нашего производства...

В прошлых сезонах наш Гофер успел посидеть в одиночке в тюрьме ядра Linux и побывать под микроскопом в роли подопытного суслика шоу `За стеклом`. Теперь пора делать бизнес!

Мы открываем Завод `"ООО Gopher-shop"` - гигантское промышленное предприятие по производству и обработке заказов.
Но на любом заводе без жестких ГОСТов наступает разруха. Ленивые рабочие пытаются протащить в сборочный цех левые детали и кривые чертежи, то есть `YAML манифесты` без лимитов ресурсов, без опознавательных знаков и с деталями из сомнительных реестров образов. Руками проверять каждую гайку нереально, брак тихо уедет к клиентам. Вдобавок БД требует постоянных пинков инженера, а дирекция завода `control plane` в любой момент может уйти на забастовку...

В этом сезоне мы строим полностью автономную и защищенную от дурака фабрику:

- Жесткий Ростехнадзор `Kyverno`. Ставим на проходной автоматический детектор брака. Если чертеж нарушает правила, система физически закрывает ворота и бьет инженера по рукам.
- Конвейерная автоматизация `Helm`. Пишем единый генеральный план завода. Будем менять станки на ходу без остановки производства и мгновенно сжигать бракованные партии апдейтов.
- Робот-Завскладом `Оператор БД`. Увольняем инженера с лопатой, к большому сожалению. Наша база данных теперь управляется умным роботом, который сам чинит станки и быстро ликвидирует аварии. Будущее наступило...
- День независимости цехов `Падение control plane`. Устроим жесткий саботаж и полностью отключим Главный Штаб Управления. Докажем, что наши рабочие у станков продолжают штамповать детали по старой памяти, даже когда руководство лежит в нокауте.

Ну и в качестве бонуса мы натягиваем систему датчиков и пожарную сирену `ServiceMonitor` и `PrometheusRule` поверх нашего старого промышленного комбайна из второго сезона.

Испытательный полигон: Локальный цех `OrbStack`.

Нус, поехали, запускаем турбины!

### Кастинг на должность начальника охраны: Kyverno против Gatekeeper

Перед запуском конвейеров нужно выбрать главу безопасности для нашего завода. На собеседование пришли двое:

- `Мастер Kyverno` - наш выбор! Понятный, суровый местный мужик. Пишет должностные инструкции на чистом YAML, том же языке, на котором работают наши станки. Ставится одной командой, не ворует ресурсы фабрики и сразу выдает списки нарушителей `PolicyReport` прямо на вахте. Идеален для нашего локального `OrbStack цеха`.
- `Профессор Gatekeeper`. Заумный эксперт с кучей дипломов. Разговаривает на странном языке `Rego`, какой-то сложный `DSL`, который у нас на заводе никто ни черта не понимает. Требует нововведений, возведения отдельного КПП `admission контроллер`, да еще и жрет оперативку на проходной как не в себя.

Вердикт директора завода: Берем `Kyverno`. Меньше бюрократии, ниже порог входа, быстрее запустим конвейер.

## Часть 0 - Сервисы. Сюжетная арка: Запуск сборочной линии

### Шаг 0.1 - Сборка станков

Разделяем обязанности на нашем производстве микросервисов приложения `shop`:

- `api`, синхронный цех, принимает входящий трафик, проверяет чертежи заказов и фиксирует их на складе.
- `worker`, асинхронный конвейер, в фоновом режиме разгребает завалы на складе и обрабатывает очереди.

Вся доменная логика работы со складом и шпионские датчики слежения упакованы в изолированный ящик `internal/`, чтобы не плодить дубликаты на рабочих верстаках.

- Отказоустойчивый запуск `internal/db/db.go`. База данных `PostgreSQL` при первом запуске может долго раскочегариваться. Чтобы Гофер не паниковал и не улетал в аварийный рестарты, в пул `pgxpool` встроен механизм ожидания, сервис делает до `30 попыток подключения` с интервалом в `2 секунды`, терпеливо дожидаясь готовности склада.
- Конвейер без драки за заказы. Когда мы начнем масштабировать воркеров пачками, несколько роботов могут одновременно схватить один и тот же заказ. Чтобы избежать производственных травм и `double-processing`, на уровне SQL-запросов применена конструкция `SELECT ... FOR UPDATE SKIP LOCKED`. Теперь каждый воркер мгновенно блокирует свою деталь, а остальные роботы просто пропускают ее и идут дальше по конвейеру.
- Искусственный инфаркт для тестов `cmd/api/main.go`. В эндпоинт `GET /health` на `порту 8080` вшит секретный триггер. Если подкинуть станку переменную окружения `HEALTH_FAIL=true`, он моментально переключается на выдачу кода `503 Service Unavailable`. Эта фича нам жизненно необходима, чтобы проверить реакцию проходной `Kyverno` и завалить `rolling update` в будущем.
- Фоновый аудит `cmd/worker/main.go`. Наш воркер не просто молча обрабатывает заказы `раз в 2 секунды`, а параллельно поднимает независимый порт `8081` с ручками `/health` и `/metrics`, чтобы датчики `Prometheus` из второго сезона могли непрерывно считывать его пульс.

## Часть 1 - Ограждения на кластер. Сюжетная арка: ГОСТы

### Шаг 1.1. Начальник охраны

Ставим систему автоматического контроля брака Kyverno в отдельный загон с помощью `Helm`:

```bash
helm repo add kyverno https://kyverno.github.io/kyverno/
helm repo update
helm install kyverno kyverno/kyverno -n kyverno --create-namespace
```

Контроллеры успешно запустились и встали на дежурство:

```bash
kubectl get pods -n kyverno
```

![](img/02_kyverno_pods.png)

Все правила пишем через классические манифесты `ClusterPolicy`. Этот синтаксис полностью поддерживается, наглядно описывает правила и готов к жесткой фильтрации входящих чертежей.

---

### Шаг 1.2. Лимиты цехов

Для защиты завода от перегрузки подстанции вводим обязательные нормативы. Политика `require-resources` запрещает запуск оборудования без четких границ по памяти и процессору.

Включаем систему защиты:

```bash
kubectl apply -f policies/01_require_resources.yaml
```

Попытка протащить чертеж без ограничений сразу вызвала ресурсный голод. Охрана нашла контейнер без ресурсного паспорта и заблокировала деплой, чтобы нода не упала в обморок:

```bash
kubectl apply -f policies/violations/01_no_resources.yaml
```

![](img/03_violation_no_resources.png)

Кластер надежно застрахован от прожорливого оборудования..

---

### Шаг 1.3. Контрабанда сырья

Для защиты сборочных цехов от левых материалов вводим жесткий пограничный контроль. Правило `trusted-registry` закрывает доступ для любых внешних деталей, кроме проверенных официальных образов `docker.io/library/*` и наших личных локальных сборок `shop-api` и `shop-worker`.

Запускаем сканирование грузов на проходной:

```bash
kubectl apply -f policies/02_trusted_registry.yaml
```

Таможня Гофера моментально обнаружила контрабанду из серого реестра. Автоматика объявила план-перехват и депортировала нелегальный контейнер на этапе создания:

```bash
kubectl apply -f policies/violations/02_bad_registry.yaml
```

![](img/04_violation_bad_registry.png)

Черный импорт успешно остановлен, ворота закрыты для сомнительных поставщиков.

---

### Шаг 1.4. Маркировка деталей

Для наведения порядка на складе вводим жесткую паспортизацию. Политика `require-labels` требует обязательного наличия меток `app` и `owner` на каждом поде, чтобы сетевые службы и датчики мониторинга могли мгновенно находить оборудование.

Применяем регламент маркировки:

```bash
kubectl apply -f policies/03_require_labels.yaml
```

Когда в цех попытались протащить деталь без опознавательных знаков, автоматика заблокировала деплой. Гофер потерял клеймо, а без документов в этот кластер вход закрыт:

```bash
kubectl apply -f policies/violations/03_no_labels.yaml
```

![](img/05_violation_no_labels.png)

Все немаркированные ресурсы успешно отсекаются на проходной!

---

### Шаг 1.5. Режим секретности

Для защиты операционной системы завода от захвата контроля вводим жесткие инструкции по безопасности. Политика `no-privileged` полностью запрещает запуск контейнеров с флагами `privileged: true` и `allowPrivilegeEscalation: true`, блокируя любые попытки скрытого повышения прав процессов.

Активируем режим повышенной безопасности:

```bash
kubectl apply -f policies/04_no_privileged.yaml
```

Когда один из сотрудников попытался протащить чертеж с требованием выдать ему ключи от главного сейфа хоста, автоматика пресекла нарушение на входе:

```bash
kubectl apply -f policies/violations/04_privileged.yaml
```

![](img/06_violation_privileged.png)

Чтобы система не сыпала ложными тревогами, когда инженеры вообще не запрашивают этот блок настроек, мы применили условный оператор `=(securityContext)`. Если блока прав в чертеже нет, система спокойно пропускает его дальше, а блокирует только явных узурпаторов с флагом `true`.

---

### Шаг 1.6. Финальный аудит

Для исключения неопределенности на линии запрещаем использование деталей без точной маркировки. Политика `no-latest-tag` блокирует любые чертежи с тегом `:latest` или вовсе без указания версии. Без точных номеров партий инженеры не поймут, что реально работает на станках, а автоматический откат брака станет невозможен.

Внедряем запрет на лотерею версий:

```bash
kubectl apply -f policies/05_no_latest_tag.yaml
```

Попытка пропихнуть деталь с тегом `latest` была мгновенно пресечена. Гофер требует ясную версию, лотерея официально окончена:

```bash
kubectl apply -f policies/violations/05_latest_tag.yaml
```

![](img/07_violation_latest_tag.png)

Итог контроля безопасности: на заводе развернуты и переведены в боевой режим `Enforce` все пять защитных политик:

```bash
kubectl get clusterpolicy
```

![](img/08_all_policies.png)

Каждый регламент успешно прошел краш-тесты вредоносными чертежами из папки `violations`. Автоматика отсекает брак на входе, не давая ему дойти до `etcd кластера`. Столбцы подтверждают статус контура: `ADMISSION=true` перехватывает манифесты на лету, `BACKGROUND=true` непрерывно сканирует цеха, а статус `READY=True` гарантирует, что Ростехнадзор Гофера полностью готов к защите производства.

![](img/1_1_gopher.png)

## Часть 2 - Чарт api и worker. Сюжетная арка: Бесперебойное производство

В шаблоны жестко закладываем ГОСТы: клейма `app` и `owner`, `лимиты ресурсов` и `проверенные образы`. Для работы без простоя прописываем обновление строго по одному станку через параметры `maxSurge: 1` и `maxUnavailable: 0`, а проверку пульса вешаем на `/health`

Проверяем чертежи на корректность:

## Часть 4 - Падение control plane. Сюжетаня арка: Пульт управления

### Шаг 4.1. Проверка ограничений

По инструкциям требовалось отключить главный пульт управления завода `etcd` или `kube-apiserver`. Однако на нашей платформе OrbStack сделать это напрямую невозможно:

- Наш стенд работает на встроенном монолите `k3s`, который намертво вшит в системную виртуальную машину кластера.
- Управляющий штаб не вынесен в отдельные контейнеры или поды. Команда `docker ps` видит только рядовые станки, а проверка сектора `kube-system` отображает лишь сетевые службы.
- Доступа к внутренним процессам через `утилиту orbctl` нет, а единственный системный переключатель `vmcontrol.sock` рубит всю виртуальную машину целиком, и вместе со штабом могут упасть и рабочие цеха, что нарушает правила теста.
  Прямая остановка управляющих органов без отключения всего завода невозможна!

### Шаг 4.2. Обрыв связи

Для проверки независимости цехов от главного управления имитируем полную потерю связи с диспетчерской. Создаем копию плана с заведомо неверным адресом коммутатора, оставив оригинальные провода целыми:

```bash

sed -i '' 's/:26443/:29999/g' ./kubeconfig-broken.yaml
```

Пробуем запросить рапорт о состоянии оборудования через поврежденную линию связи:

```bash
KUBECONFIG=./kubeconfig-broken.yaml kubectl get nodes
```

Система выдает отказ, связь полностью заблокирована.

При этом станки в цехах продолжают работать в автономном режиме. Выделенная телефонная линия, запущенная до обрыва, держит соединение, и контрольный запрос к датчику здоровья `/health` возвращает стабильный `код 200`:

```bash
# 200
```

Испытание подтвердило, что сборочные линии и склады сырья никак не зависят от падения главного штаба управления.

### Шаг 5.2. Критические пороги

Внедряем шаблон `templates/prometheus-rules.yaml`, содержащий три критических порога для сигнальных реле. Ресурс маркируем штампом `release: kube-prom`, чтобы центральный пульт КИПиА автоматически взял правила на вооружение.

Запускаем обновление настроек:

```bash
helm upgrade shop charts/shop -n shop
kubectl get prometheusrule -n shop
```

![](img/30_prometheus_rules.png)

Назначение и обоснование уставок:

- `ApiHighErrorRate` (Критический брак)
  Суть: Доля бракованных ответов 5xx превышает 5% за 5 минут, и сбой держится 2 минуты.
  Обоснование: Если каждый двадцатый сигнал идет с ошибкой, то это системная авария, блокирующая отгрузку продукции. Порог в 5% отсекает случайные разовые колебания, а задержка в 2 минуты бережет систему от ложных тревог при плановом перезапуске оборудования.

- `ApiHighLatencyP95` (Замедление конвейера)
  Суть: Время отклика станков по 95-му перцентилю превышает 1 секунду на отрезке в 5 минут, и задержка длится более 2 минут.
  Обоснование: Торможение конвейера срывает темпы выдачи плана. Расчет по `P95` игнорирует редкие единичные аномалии и показывает реальную картину работы для абсолютного большинства агрегатов, фиксируя границу комфортного ожидания.

- `ApiDown` (Остановка цеха)
  Суть: На пульте КИПиА полностью исчезли сигналы от живых реплик цеха `api` в течение `1 минуты`.
  Обоснование: Означает полный паралич производственной линии. Минутная пауза не дает сработать сирене во время штатной замены агрегатов. Функция `absent()` гарантированно перехватывает ЧП, когда датчики вообще перестают слать телеметрию, например, при случайном списании всех станков.

### Шаг 5.3. Проверка сигнализации

Для сквозной проверки аварийной цепочки намеренно закладываем дефект в логику станка `api` - ручку `/fail`, которая всегда сыплет браком с `кодом 500`. Пересобираем прошивку приложения с номером партии `1.0.2` и обновляем генеральный план:

```bash
docker build --target api -t shop-api:1.0.2 .
helm upgrade shop charts/shop -n shop
```

Чтобы проверить реакцию приборов, пускаем по линии непрерывный поток бракованных деталей:

```bash
while true; do curl -s -o /dev/null http://localhost:8080/fail; sleep 0.1; done
```

Спустя 2 минуты непрерывного потока брака реле `ApiHighErrorRate` замкнуло контакты, Пульт КИПиА перевел сигнал из режима ожидания в боевой статус `FIRING`.

![](img/31_prometheus_alerts_firing.png)

Служба `Alertmanager` мгновенно перехватила этот сигнал и вывела тревожную карточку на диспетчерский экран `Karma`. На табло включилась аварийная сирена, выдав четкую инженерную сводку: `Брак пробил потолок. Доля 5xx за 5 минут: 79.52%. АЛАРМ: api-service безудержно плюется пятисотками!`.

![](img/32_karma_alert_firing.png)

Генеральный итог испытаний: вся цепочка от настройки критических порогов в чертежах до сирены на табло диспетчера отработала безупречно, подтвердив полную готовность контура КИПиА к автоматическому контролю производства.
